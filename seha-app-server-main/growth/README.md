# وحدة النمو والإدارة

منظومة مستقلة داخل المشروع لإدارة الباقات والأرصدة والكوبونات والإحالات
والحملات والمكافآت والصلاحيات — تُدار كلها من لوحة التحكّم دون تعديل كود.

## المبدأ الحاكم

> قاعدة البيانات هي مصدر الحقيقة، والكود يحرس الثوابت.

الأدمن يغيّر **بارامترات تجارية** من اللوحة فتسري فوراً. ولا يستطيع أحد —
ولا مالك النظام — تعطيل **ثوابت النظام** لأنها مفروضة في الكود وفي قيود
قاعدة البيانات معاً.

## التركيب

```
growth/
  config/
    permissions.js       مفردات الصلاحيات — ثابتة، كل عنصر مربوط بمسار يفحصه
    invariants.js        سقوف صلبة لا يتجاوزها أي إعداد
    settingsRegistry.js  مفاتيح الإعدادات: النوع والنطاق والخدمة المستهلكة
  models/                15 نموذجاً + العلاقات
  services/              منطق الأعمال — الطبقة الوحيدة التي تكتب
  controllers/           تحقّق المدخلات وتشكيل الردود
  routes/index.js        كل مسار يعلن صلاحيته في سطره
  middlewares/           حارس الصلاحيات + مغلّف الأخطاء
  tests/                 اختبارات تكامل على قاعدة حقيقية
  bootstrap.js           قيود CHECK والفهارس الجزئية والبذور
  hooks.js               الجسر مع المنصة القائمة
```

## الاندماج مع المشروع

ثلاثة أسطر في ملفات قائمة، وصفر تعديل على أي نموذج أو وسيط أو متحكّم موجود:

| الملف | الإضافة |
|---|---|
| `config/routes.js` | تحميل `growthRoute` |
| `config/mountRoutes.js` | `{ name: 'growthRoute', at: '/growth' }` |
| `index.js` | تحميل النماذج + `growth.initialize(sequelize)` |

الواجهة: مسار واحد في `App.jsx` (`/growth/*`) ورابط في لوحة التحكّم.

حذف الوحدة = حذف `growth/` وهذه الأسطر.

## الثوابت المالية

| # | الثابت | كيف يُفرَض |
|---|---|---|
| I1 | `credit_balance == SUM(ledger)` | الطرفان يُكتبان في معاملة ذرّية واحدة |
| I2 | `credit_balance >= 0` | فحص تحت القفل + قيد `CHECK` في القاعدة |
| I3 | سلسلة الحركات متّصلة | قيد `CHECK` على كل سطر + ترتيب داخل المعاملة |
| I4 | أثر at-most-once | `UNIQUE(idempotency_key)` |
| I5 | الدفتر لا يُعدَّل ولا يُحذف | التصحيح بحركة تعويضية فقط |

`credit.service` هو **الكاتب الوحيد** لأي رصيد. كل مسار يمرّ منه، وكل عملية
تقفل صفّ الملف بـ `SELECT … FOR UPDATE` قبل أن تحسب شيئاً.

### لماذا لا تُصحَّح المطابقة تلقائياً

`reconcile()` تُبلّغ ولا تكتب. التصحيح الصامت يخفي الخلل الذي سبّب التباين،
وهو أخطر من التباين نفسه.

## اللقطة التاريخية

`growth_orders` ينسخ اسم المنتج وسعره وأرصدته ومزاياه وقت الشراء. تعديل
المنتج اليوم لا يعيد كتابة طلب الأمس. عرض الطلب لا يقرأ `growth_products`
إطلاقاً — المفتاح الأجنبي للنسب فقط.

## الإحالة

أحادية المستوى. القمع:

```
clicked → registered → verified → activated → meaningful_action
        → first_purchase → retained
```

الدفعات موزّعة على المراحل عبر `payout_schedule` المضبوط من اللوحة. التوزيع
الموصى به:

| المرحلة | الطرف | لماذا |
|---|---|---|
| `verified` | المُحال إليه | حافز اكتساب يصل مبكراً كفاية ليغيّر السلوك |
| `activated` | المُحيل (جزء) | دفعة سريعة تُبقيه يُحيل |
| `first_purchase` | المُحيل (الباقي) | معظم التكلفة مربوطة بإيراد فعلي |

**الاسترجاع:** إن أنفق المستفيد المكافأة، يُسترجَع المتاح ويُسجَّل الباقي في
`reward_debt` تُخصم منه المنح القادمة — فيُحفظ عدم السالبية ولا يتسرّب مال.

## كشف الاحتيال

تسع إشارات موزونة ⇒ نطاق `low` / `medium` / `high`.

**ملاحظة خاصة بهذا المنتج:** مستخدموه أطباء وموظفو مستشفيات خلف NAT مشترك،
فتطابق الـ IP هنا هو القاعدة لا الاستثناء — ووزنه وحده +5 فقط.

الإجراء الوحيد المسموح هو **تعليق دفعة**، لا حظر حسابات. التعليق قابل
للاسترجاع والحظر بالاستدلال ليس كذلك. المخاطرة المتوسطة تدفع للمُحال إليه
وتعلّق المُحيل فقط.

## انتهاء صلاحية أرصدة الاشتراك

معطّل افتراضياً. حين يُفعَّل من الإعدادات، يُشغَّل المسح من صفحة الأرصدة
(تبويب «انتهاء الصلاحية») بمعاينة أولاً ثم تنفيذ.

قاعدة الإسناد: **الاستهلاك يُخصم من أرصدة الاشتراك أولاً** — فتبقى أرصدة
الحزم والمكافآت أطول ما يمكن، وهو ما يصبّ في مصلحة العميل.

```
المنتهي = max(0, منح الاشتراك − كل الاستهلاك − ما سبق إنهاؤه)
          مقصوصاً عند الرصيد الحالي (حفظاً للثابت I2)
```

مثال: مُنح 300 باشتراك و50 بحزمة، أنفق 100 ⇒ رصيده 250، يُنهى 200 ويبقى 50.

**أرصدة حزم الشراء لا تنتهي أبداً** — العميل دفع ثمنها مرة واحدة ولم يستأجرها.

## الإعدادات

كل مفتاح في `settingsRegistry.js` يعلن نوعه ونطاقه و**الخدمة التي تقرؤه**.
مفتاح لا يقرأه شيء لا يُعرَض أصلاً: «إعداد قابل للتعديل ويتجاهله الخادم»
يخدع المشغّل.

لا يوجد cache عابر للطلبات — التغيير يسري فوراً. القيم الرقمية تُقصّ عند
نطاقها بدل أن تُرفض، ويُبلَّغ المشغّل بما قُصّ.

## حواجز على الضبط نفسه

| الحاجز | السبب |
|---|---|
| كوبون بلا سقف ولا انتهاء مرفوض | ثلاثة حقول فارغة = منحة لا نهائية |
| نسبة الخصم تُقصّ عند 100% | ما فوقها خطأ منطقي |
| المنحة الواحدة مقصوصة عند سقف صلب | حاجز ضد خطأ مدخل |
| أنواع أحداث المكافآت قائمة مغلقة | قاعدة بنوع مجهول لن تُطلَق أبداً |
| مفردات الصلاحيات ثابتة | صلاحية مخترَعة لا يفحصها مسار |
| الأدوار النظامية لا تُجرَّد صلاحياتها | يمنع قفل الجميع خارج النظام |

## ما كشفته المراجعة الأمنية

مراجعة مستقلة على الوحدة كاملة وجدت ثلاث نقاط، أُصلحت كلها وصار لكل واحدة
اختبار انحدار **ثبت أنه يفشل بدون الإصلاح**:

| النقطة | الخطر | الإصلاح |
|---|---|---|
| تصدير CSV لا يُحيّد الصيغ | ترويسة `X-Forwarded-For` خبيثة تصل السجل ثم تُنفَّذ كصيغة على جهاز المشغّل | اقتباس مفرد بادئ لأي خلية تبدأ بـ `= + - @`، و`net.isIP` يرفض العنوان غير الصالح قبل تخزينه |
| السقف لكل مستخدم في الكوبون بلا قفل | طلبان متوازيان يتجاوزان «مرة واحدة لكل مستخدم» معاً | قفل صفّ الكوبون (`FOR UPDATE`) قبل الفحوص في مسار الاستخدام؛ المعاينة تبقى بلا قفل |
| فحص «إنشاء طلب لغيرك» ضمنيّ | آمن بالصدفة — يعتمد على أن `/me/orders` لا يمرّ بـ `requirePermission`؛ أي فحص يُضاف مستقبلاً كان سيكسره بصمت | فحص صريح عبر `roles.has`، ورفض بـ 403 بدل التراجع الصامت |

**ملاحظة منهجية:** أول صيغة لاختبار سباق الكوبون استعملت `Promise.all` ومرّت
حتى مع الكود المعطوب — التوازي العشوائي لا يضمن الوقوع في النافذة الحرجة.
استُبدلت بمعاملتين تُقادان يدوياً، فصارت تفشل بلا القفل وتنجح معه.

## الاختبارات

```bash
TEST_DATABASE_URL=postgresql://user@host:5432/growth_test npm run test:growth
TEST_DATABASE_URL=postgresql://user@host:5432/growth_test npm run test:growth:api
```

⚠️ يشغّلان `sync({ force: true })` فيمسحان كل الجداول. استعمل قاعدة اختبار
منفصلة.

```bash
TEST_DATABASE_URL=... npm run test:growth:flow   # الحلقة كاملة
TEST_DATABASE_URL=... npm run test:growth:all    # الثلاثة معاً
```

- `invariants.test.js` — 69 تأكيداً: الثوابت، التزامن، اللقطة التاريخية،
  الإحالة، الاسترجاع، انتهاء الصلاحية، محرك المكافآت، الصلاحيات، التدقيق.
- `api.test.js` — 55 تأكيداً عبر HTTP: التفويض، التحقّق، دورة الإعداد
  كاملة، اللقطة، سريان الصلاحيات، التدقيق.
- `customer.test.js` — 41 تأكيداً للحلقة كاملة عبر **متحكّمات المنصة
  الحقيقية**: إنشاء حساب ← ملف تجاري ← إسناد إحالة ← إصدار مستند ← تفعيل ←
  دفعة المُحيل ← شراء ← بقية الدفعة، وعزل بيانات العملاء عن بعضهم.

## المسارات العامة

أربعة فقط، ولكلٍّ سبب:

| المسار | لماذا بلا مصادقة |
|---|---|
| `GET /growth/public/settings` | واجهة العميل تحتاج رقم الدعم وتعليمات الدفع قبل الدخول |
| `GET /growth/public/products` | صفحة الباقات تُعرض للزائر |
| `GET /growth/r/:code` | النقرة تسبق وجود الحساب |
| `POST /growth/public/coupons/validate` | يحسب الخصم ولا يغيّر شيئاً ولا يستهلك سقفاً |

المفاتيح العامة محدّدة بـ `public: true` في السجل — ولا يتسرّب غيرها.

## نقاط الوصل مع المنصة

الخطّافات موصولة فعلاً — بدونها يبقى القمع ميتاً و MAPU صفراً مهما بدت
الوحدة مكتملة:

| الموضع | الخطّاف | الأثر |
|---|---|---|
| `controller/users.controller.js` بعد إنشاء المستخدم | `onUserRegistered` | ملف تجاري + رصيد ترحيبي + إسناد إحالة إن حمل الطلب `referral_code` |
| `controller/leaves.controller.js` بعد إنشاء الإجازة | `onDocumentCreated` | خصم الاستخدام + تسجيل التفعيل + تقدّم القمع + تقييم المكافآت |

كلاهما يفشل بصمت: عطل في النمو لا يمنع طبيباً من إصدار إجازة، ولا يمنع
إنشاء حساب.

### تشغيل الاقتصاد

`onDocumentCreated` يقبل `enforce` وهو `false` افتراضياً: الوحدة تُركَّب دون
أن تغيّر سلوك المنصة — يُسجَّل الاستخدام ويتقدّم القمع، لكن نقص الرصيد لا
يمنع الإصدار. حين يقرّر صاحب المنتج تشغيل الاقتصاد فعلياً، يُمرَّر
`enforce: true` من `leaves.controller` فيصير نقص الرصيد مانعاً.

## واجهة العميل

| المسار | الوصف |
|---|---|
| `/packages` | الباقات والحزم — عامة، بأسعار وتعليمات من الإعدادات |
| `/my-account` | الرصيد والطلبات وإثبات الدفع ورابط الإحالة |
| `/r/:code` | هبوط الإحالة — يسجّل النقرة ويُظهر الرمز |

**ملاحظة عن هذا المنتج:** لا يوجد تسجيل ذاتي — الحسابات يُنشئها الفريق. لذلك
صفحة الهبوط لا تدّعي أن الزائر سيسجّل بنفسه، بل تُظهر له الرمز وتوصله بواتساب
بالرمز مُعبّأً؛ ويُدخله المشغّل في حقل «رمز الإحالة» عند إنشاء الحساب من
صفحة إدارة المستخدمين. الرمز يُحفظ محلياً أيضاً، فإن أُضيف تسجيل ذاتي لاحقاً
يعمل الإسناد تلقائياً بلا تغيير.
